2. Introduction

Course registration is one of the most important events for every student at VIT each semester. Under the Fully Flexible Credit System (FFCS), students have the freedom to pick their courses, select their professors, and create a custom timetable of lecture and lab slots (such as A1, B1, C1, L1+L2, etc.).

While this flexibility is great, it also creates common real-world challenges: students can accidentally pick overlapping time slots, popular courses get filled in seconds with no automatic waitlist to promote students when someone drops, credit limits need to be tracked, and maintaining the mandatory 75% attendance rule is critical to avoid being debarred from the Final Assessment Test (FAT).

I built SmartCampus 360 to address these exact problems. Developed in pure Java 21, it is a modular, console-based academic management system that applies core Object-Oriented Programming (OOP) principles learned in CSE2006. It features automated timetable clash detection, fair FIFO waitlist management with automatic promotion on drops, 27-credit limit enforcement, real-time attendance tracking, dynamic CGPA computation, and persistent CSV storage.

3. Problem Statement

During course registration and throughout the academic semester, students and faculty face several practical issues:

  • Timetable Slot Clashes: It is easy for students to accidentally pick subjects that take place during the same hour (for instance, two courses scheduled on Slot A1, or a 2-hour lab slot like L1+L2 overlapping with an afternoon lecture).
  • Lack of Automated Waitlist Promotion: When a course reaches capacity, students are blocked. If an enrolled student drops the course later, there is no automatic system to immediately promote the next student in line.
  • Credit Overload: Students are restricted to a maximum of 27 credits per semester. Without automated checks during registration, students can exceed this limit.
  • Attendance Debarment Risk: At VIT, maintaining at least 75% attendance is mandatory. Students often realize their attendance has fallen below 75% too late to take corrective action.
  • Scattered Academic Tracking: Calculating weighted CGPA and viewing course fee breakdowns often require separate tools rather than an integrated platform.

5. Non-Functional Requirements

  • Performance: Instant in-memory lookups using ConcurrentHashMap execute in sub-millisecond time.
  • Security: Clear role separation prevents students from editing grades or courses. Passwords support SHA-256 hashing.
  • Usability: Formatted console output with tables, dividers, and a built-in automated --demo flag for quick grading.
  • Reliability & Persistence: Saves all user, course, and registration records to CSV files in data/ so state survives restarts.
  • Concurrency: Thread-safe seat allocation and a background daemon worker using BlockingQueue for async alerts.
  • Maintainability: Clean package structure (model, service, repository, exception, concurrency).

8. Design Decisions & Rationale

  1. Inheritance for Courses (Theory vs Lab): Instead of using messy flags like boolean isLab, I created an abstract Course class and extended it into TheoryCourse and LabCourse. This allows clean, polymorphic fee calculation without conditional checks.
  2. Custom Domain Exceptions: Rather than throwing generic exceptions, I created domain-specific exceptions (SlotClashException, CreditLimitExceededException, CourseFullException). This makes error handling clear and lets the UI show exact reasons when an action fails.
  3. FIFO Queue for Waitlists: Fairness is essential in course registration. I used Java's LinkedList implementing the Queue interface so waitlisted students are queued strictly in the order they applied.
  4. File-Based CSV Storage: To keep the project completely portable without requiring external database setups (like MySQL or Oracle), I built a CSV storage manager using Java NIO.2. Anyone with JDK 21 can clone and run it immediately.
  5. Background Worker Thread: To simulate real-time notification alerts without freezing the console interface, I used a dedicated daemon thread running a BlockingQueue.

9. Implementation Details

The project is built entirely on standard Java 21 features with zero external runtime dependencies:

  • Encapsulation: Private fields with explicit accessors/mutators and immutable collections (Collections.unmodifiableList).
  • Collections Framework: ConcurrentHashMap for thread safety, LinkedHashSet for student rosters, and LinkedList for FIFO waitlists.
  • Regular Expressions: InputValidator validates registration numbers (e.g., 25BAI10611) and course codes (e.g., CSE2006).
  • File I/O (NIO.2): Utilizes Files.newBufferedReader() and BufferedWriter for clean CSV parsing and serialization.

11. Testing Approach

Quality assurance was achieved through automated unit testing and full system demonstration:

  • Unit Testing (SystemTestSuite): Contains 11 tests validating inheritance, slot clash detection, credit overloads, waitlist promotions, grading calculations, and CSV persistence.
  • Automated Demonstration (Main --demo): Executes an end-to-end integration walkthrough covering all user workflows without requiring manual input.

12. Challenges Faced & How I Solved Them

  • Handling Compound Timetable Slots: In VIT's timetable, labs occupy compound slots like L1+L2. A simple string match failed when comparing with a single slot L1. I tokenized slot codes on + into a Set<String> so collision checks check set intersections.
  • Race Conditions in Waitlist Promotion: Multiple simultaneous drops could cause inconsistent seat counts. I synchronized critical seat allocation methods and used ConcurrentHashMap for storage maps.
  • Incomplete Courses in CGPA: Ungraded courses were skewing CGPA. I updated the calculation to sum only graded credits, preventing division by zero or inaccurate averages.

13. Learnings & Key Takeaways

  • Real Value of OOP: Building Course, TheoryCourse, and LabCourse with polymorphic fee calculations showed me how clean and extensible object-oriented code is compared to nested if-else checks.
  • Java Collections in Practice: Choosing the right data structure matters—using Set for duplicate checks, Queue for fair waitlisting, and Map for instant lookups made the system fast and readable.
  • Thread Safety: Learning how to use daemon threads, BlockingQueue, and synchronized blocks showed me how real backend systems handle background tasks safely.
  • Defensive Programming: Writing custom exceptions and input validators helped me catch bugs early before they corrupted stored data.
