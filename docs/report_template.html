2. Introduction

Higher education academic operations represent a complex orchestration of student preferences, faculty loads, time slot constraints, prerequisite validations, and room capacities. In institutions utilizing modern academic models such as the Fully Flexible Credit System (FFCS), students select their desired courses, faculty members, and scheduling slots dynamically. Without strict algorithmic governance, issues like timetable slot clashes, credit limit exceedance, and inefficient section queueing can emerge.

SmartCampus 360 is a high-performance, modular academic management engine engineered entirely in Java 21. It models academic entities (students, faculty, administrators, theory lectures, and computer laboratories) into a cohesive Object-Oriented architecture. The project demonstrates real-time slot conflict resolution, credit regulation, fair FIFO waitlisting, dynamic 10-point CGPA recalculation, and background multithreaded notification dispatching.

3. Problem Statement

University enrollment and student management systems face systemic operational hurdles:

  • Timetable Slot Collisions: In complex timetables (e.g. morning/evening shifts with compound laboratory blocks), students often register for overlapping classes.
  • Manual Waitlist Processing: When popular courses reach seat limits, students are forced to continually refresh web pages. Vacant seats resulting from drops often go unutilized.
  • Credit Overload: Lack of atomic validation allows students to exceed academic credit caps (27 credits/semester), complicating degree auditing.
  • Attendance Debarment Risk: Failure to provide real-time attendance warnings leads to surprise debarments when students drop below the mandatory 75% threshold.

5. Non-Functional Requirements

  • Performance: In-memory lookups via ConcurrentHashMap execute in \(O(1)\) time complexity. Conflict detection runs in \(O(K)\) where \(K\) is current registrations.
  • Security: Clear separation of roles via RBAC. Sensitive data and credentials are kept encapsulated and hashed.
  • Reliability & Persistence: Persistent state synchronization through CSV file I/O ensuring data durability across system reboots.
  • Concurrency & Thread Safety: Non-blocking background event dispatching using BlockingQueue and daemon threads.
  • Maintainability: Clean architecture strictly adhering to SOLID principles and package modularity.

8. Design Decisions & Rationale

  1. Polymorphic Architecture: Rather than relying on conditional branching with flags, `TheoryCourse` and `LabCourse` extend `Course` and override `calculateTuitionFee()`, cleanly capturing domain variations.
  2. Custom Domain Exception Hierarchy: Replacing generic runtime exceptions with domain-specific classes (`SlotClashException`, `CreditLimitExceededException`, `CourseFullException`) provides clear feedback to users.
  3. Repository Pattern with File Synchronization: The `DataStore` interface decouples the services from storage mechanisms, allowing seamless transitions between in-memory collections and persistent CSV files.
  4. Asynchronous Daemon Worker: The `NotificationWorker` implements `Runnable` and uses a thread-safe `BlockingQueue` to process alerts without degrading application responsiveness.

9. Implementation Details

The project is built entirely on standard Java 21 features with zero external runtime dependencies:

  • Encapsulation: Private fields with explicit accessors/mutators and immutable collections (`Collections.unmodifiableList`).
  • Collections Framework: ConcurrentHashMap for thread safety, LinkedHashSet for ordered student rosters, and LinkedList for FIFO waitlisting.
  • Regular Expressions: InputValidator validates registration numbers (e.g., 25BAI10611) and course codes (e.g., CSE2006).
  • File I/O (NIO.2): Utilizes Files.newBufferedReader() and BufferedWriter for CSV parsing and serialization.

11. Testing Approach

  • Unit Testing (SystemTestSuite): Contains 11 tests validating inheritance, slot clash detection, credit overloads, waitlist promotions, grading calculations, and CSV persistence.
  • Automated Demonstration (Main --demo): Executes an end-to-end integration walkthrough covering all user workflows without requiring manual input.

12. Challenges Faced

  • Compound Slot Clashes: Handling composite laboratory slots (e.g. L1+L2) required tokenization and set overlap algorithms.
  • Atomic Waitlist Promotion: Preventing race conditions during simultaneous drops and adds required thread synchronization.
  • Incomplete Courses in GPA: Ungraded courses were excluded from GPA weight calculations to prevent skewed semester results.
